# ADR-0003: Two installs, a CLI plugin and a checksummed project install

Status: accepted
Date: 2026-11-09

## Context

Until now the only way to use this port was to copy `.github/` and `shipyard/` into a repository, or to create a
repository from this one as a template. That reaches every Copilot client, but it has no update path and no
uninstall, and it puts a large tree into every project. Copilot CLI has a plugin system (`copilot plugin install
owner/repo`) with a `plugin.json` manifest that can carry agents, skills, hooks and dynamic-workflow extensions, and
`copilot plugin uninstall <name>` removes it again. The cloud coding agent and the IDEs do not load CLI plugins; they
read `.github/` from the repository.

Probed on CLI 1.0.107 with `copilot --plugin-dir`:

- The legacy manifest's path keys (`agents`, `skills`, `extensions`, `hooks`) accept the folders this repository
  already has (`.github/agents`, `.github/skills`, `.github/extensions`), so one set of files serves both installs.
- `${PLUGIN_ROOT}` is expanded in a plugin hook's `bash` command; the hook runs with the plugin folder as its
  working directory and gets the project as `COPILOT_PROJECT_DIR`.
- Plugin agents are namespaced `<plugin>:<agent>`; a project `.github/agents/` file with the same id wins silently.
- A plugin's workflows register without the project being a trusted folder; the project's own `.github/extensions/`
  need trust.
- A symlinked `extensions/` folder is not followed; the manifest key is.

## Decision

1. **Ship the repository as a Copilot CLI plugin named `shipyard`.** `plugin.json` and `hooks.json` at the root
   are generated by `shipyard/scripts/gen_plugin.py` from `package.json` and `.github/hooks/shipyard.json`; CI
   fails when they drift. The hook file rewrites every command to `python3 "${PLUGIN_ROOT}/shipyard/scripts/hooks/
   <hook>.py"` and drops `cwd`. Install: `copilot plugin install vineethvarghese/shipyard-copilot`. Uninstall:
   `copilot plugin uninstall shipyard`. Agent ids become `shipyard:shipyard-<short>`; `role_from_name` in the hook
   adapter and `pluginAgentPrefix()` in the workflow library strip or add that prefix.
2. **Add a project installer with an uninstaller for the other clients.** `shipyard/scripts/install.py` has
   `init`, `update`, `status` and `remove`. It copies a fixed component list (never this repository's own tests,
   sources, CI or plugin files), records every file's SHA-256 in `shipyard/INSTALL.json`, refuses to overwrite a
   differing file unless told (`--skip <glob>` or `--force`), replaces only unchanged files on `update`, deletes
   only still-matching files on `remove`, prunes the folders it emptied, and never touches `.ai/`. The installer is
   itself installed, so `remove` needs no download. `install.sh` at the root is a bootstrap that shallow-clones the
   repository and runs `init`, `update` or `status`.
3. **Do not merge the two.** The docs say to pick one per project: Copilot runs project hooks and plugin hooks
   both, so a project with both would see every deny twice.
4. **No marketplace yet.** A marketplace needs a second repository with `marketplace.json`; a direct install from
   the repository covers the need today.

## Consequences

- A project that uses Shipyard through the plugin keeps only `.ai/` in its tree. The prompt files, the Actions,
  the rulesets and the templates are not available there; those belong to the project install.
- `copilot plugin update shipyard` and `install.py update` are the two update paths; `install.py status` shows
  which installed files were edited locally.
- The upstream wording check in `gen_agents.py` accepts `shipyard:shipyard-<short>` so the coordinator can name
  plugin ids.
- Open: the `powershell` form of the plugin hooks, and `ctx.agent` with a namespaced `agent` option, are not yet
  observed. `docs/workflows.md` and `docs/hooks.md` list what was verified and what was not.
